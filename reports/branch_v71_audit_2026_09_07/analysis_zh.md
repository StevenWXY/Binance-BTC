# Binance-BTC-wzy 的 V7.1 与三分支回测差异分析

审计日期：2026-09-07。结论依据固定提交的源码、已提交报告，以及本次完成的 12 组全周期逐分钟重跑。

## 1. 结论

主要差异来自 **WZY 改写了 V7.1 的信号层，并给三个比较组统一套用了更严格的账户回撤控制**。手续费返佣、maker 报价和不同截止日期又造成其他报告之间的差异。

本次用同一份本地行情精确复现了原版 V7.1 的 728,076.22 USDT、返佣版的 844,208.61 USDT、main 原生 V4.3 的 453,890.61 USDT，以及 WZY 最新三组报告。因此，这些已核实的差异有明确的代码和配置解释。

WZY 文档中的 `xuyujian_v71_ref` 并非原版 V7.1 信号。修正这个比较对象后，在 WZY 当前的共同执行配置下，WZY 最新候选仍然优于原版 V7.1 和 main V4.3；这个结论适用于该执行配置，不能外推为各分支原生配置下的排名。

## 3. WZY 的 V7.1 实际如何运行

策略保留日线方向过滤和 4h 的 `range / trend_up / trend_down`，再增加两层判断：

1. 根据 ADX、Choppiness、效率比、均线距离、Aroon 等计算可交易性及趋势质量。
2. 根据多空方向、日线偏置和质量得分给出禁止、试探或确认参与的许可，并约束目标仓位。

许可为零时直接空仓；趋势仓位上限还受到 `max_leverage * permission_scale` 限制。弱可交易状态增加确认等待，震荡反弹也增加独立许可判断。关闭 live protection 不会关闭这些机制。

V7.1-live 早期配置相对原版更保守：杠杆上限 6.5 降至 5.5，趋势倍率 1.7 降至 1.55，空头倍率 0.15 降至 0.10，趋势确认从 2 根增至 3 根，突破缓冲从 0.20 ATR 增至 0.25 ATR。

保护层在信号后增加 ATR 止损、止盈、移动止损、快速下跌退出、持仓时限与退出冷却。信号下一根 4h 边界生效，保护价位交给 1m 执行。常规入场/增仓尝试 maker，保护退出为 taker。

最新 V7.2 又降低风险预算（target_vol=0.78、trend_scale=1.30、short_scale=0.08），并针对低质量多头初始段缩仓、初始限制结束时强制调仓、高质量延续加仓、空头初始段缩仓、强多头放宽止损及止盈距离。这已是一条独立演化的策略。

源码定位：WZY `v71_live.py:460`、`:493`、`:553`、`:738`、`:938`、`:1328`、`:1350`、`:1599`；运行 `audit.py --prepare` 后，固定副本位于本目录 `sources/wzy/src/btc_regime/v71_live.py`。

### 4.1 参考组信号被替换

WZY `scripts/compare_three_branches_same_basis.py:78` 用 `V71LiveParams` 加载参考参数，`:86` 调用 `generate_v71_live_signals`；它没有调用原版的 `generate_v7_signals`。

在完全相同的 14,424 根 4h 数据上：

- 两者日线状态全部相同，但 4h 市场状态有 150 根不同。
- 目标仓位有 2,061 根不同，约占 14.29%；多、空、空仓方向有 876 根不同。
- 原版多头/空头信号为 3,106/2,230 根，参考版为 2,720/1,766 根。
- 全部 K 线上的平均绝对目标杠杆由 0.457 降到 0.402。
- 第一次目标差异出现在 `2020-01-23 16:00 UTC`。

只替换信号并保持原执行规则，权益由 728,076 降到 414,553。这个对照说明复制 JSON 参数、关闭两个保护开关不足以复现原策略。

另外，原信号和原执行配置分别放进 X 与 WZY 引擎，生成的权益 CSV 逐字节一致。因此，不能把该差距笼统归因于引擎记账精度或平台差异。

### 4.2 账户 governor 是本次最大影响项

| 执行规则 | 原版 V7.1 | WZY 当前 |
| --- | --- | --- |
| 回撤一档 | 20% 时目标乘 0.95 | 8% 时乘 0.80 |
| 回撤二档 | 30% 时乘 0.85 | 12% 时乘 0.50 |
| 回撤三档 | 40% 时乘 0.70 | 16% 进入 reduce-only 限制 |
| 深回撤空仓后恢复 | 无独立暂停机制 | 空仓冷却 10,080 分钟后允许最多 0.25 倍目标仓位试探 |
| 延续恢复 | 随当前回撤档位恢复 | 最新版另有回撤改善 4 个百分点后的同向增仓规则 |

WZY 脚本只构造一份 `execution`，再给三个比较组共用。即使显示名称是 main 或 xuyujian，也都受 WZY governor 约束。

原版信号、WZY maker/费用设置全部固定，仅切换 `strategy_drawdown_enabled`，权益由 1,027,552 变为 23,261；main 同样由 388,430 变为 45,281。早期大回撤之后的仓位恢复受限，显著改变后续复利路径。这不是几个基点成本差异能解释的数量级。

注意：配置与文档中的“16% -> flat”不等于代码保证立即清仓。`live_risk.py:112` 对已有同向仓位返回 `min(abs(desired), abs(current))`。本次直接验证：回撤 17%、当前 2 倍、希望 3 倍时仍返回 2 倍；空仓且未满足恢复条件时才返回零。governor 在待执行信号处理时应用，也不是每分钟独立触发的账户止损。

### 4.3 手续费、报价、时间和资本层口径

- 原版 728,076 的 taker 为 4 bps；六策略统一报告的 844,209 使用 30% 返佣，即 2.8 bps。本次只改变该参数，两个结果都精确复现。
- main 的 453,891 报告使用 taker=2.8、maker=0.14 bps，maker offset=0；WZY 使用 4、0.2 bps，offset=0.5 bps，并增加 governor。改变报价也改变能否成交，不仅改变手续费。
- 当前本地未提交的 V7.1 1,119,759.06 报告截止到 2026-09-01，不能与截止 2026-08-01 的 844,208.61 混用。本次没有重跑九月窗口。
- main 家族验证中的 V4 639,099、V4.1 671,638 截止到 2026-08-25 08:00，其日期不同于朋友数据的七月底窗口。
- main 的 V4.2 和 X 的 V7.1.3 还有中性资本覆盖层。本文比较的 main V4.3、原版 V7.1、WZY V7.1/V7.2 都是方向策略，不能再混入 combined neutral 的结果。

## 5. 为什么 WZY 自己的旧文档也对不上

旧 `three_branch_same_basis_2020_2026_08_01` 报告的权益是 main=16,621.82、参考组=14,224.49、WZY=13,054.96。报告中没有启用 recovery，而现在同名执行文件已包含 recovery=true。

从旧权益 CSV 实际核查：参考组最后一次权益变化在 `2020-06-02 20:00 UTC`，main 在 `2020-11-09 20:00 UTC`，WZY 在 `2020-11-09 16:00 UTC`。之后直到 2026 年保持水平。旧结果大量包含停止交易的时间，不能把较小回撤解读为持续交易下的低风险。

后续恢复机制和信号层都继续迭代，当前默认 V7.1-live 重跑为 12,342.48；最新 V7.2 为 57,208.63。应以具体报告中序列化的参数及执行配置解释该次结果，不能拿当前 JSON 去解释所有历史文档。

## 6. 对结果可信度的判断

最新 WZY 三组结果可复现。修正参考信号后，共同 WZY 执行配置下的排名为：V7.2 57,209 > main V4.3 45,281 > 原版 V7.1 23,261。原版参考组被误标影响数值与差距，但本次修正并未改变这一特定执行环境下的排名。

保留各自原生配置时，结果是原版 V7.1 728,076、main V4.3 453,891、WZY V7.2 57,209；对应的回撤和费用假设不同，这组不能直接用来评价谁更适合相同风险预算。

还有两项实际限制：

1. 报告的 `max_drawdown` 基于 4h 边界权益采样；WZY 还记录分钟级 governor 观察值。最新参考组分别为 -23.06% 与 -24.66%，V7.2 为 -17.17% 与 -17.61%。16% 是风控阈值，不是回撤上限保证。
2. WZY 的 `scan_risk_adjusted_weak_years.py:178` 和 `:197` 明确把 2026 收益加入候选评分，其他脚本也在全周期反复筛选。因此，2025-2026 的分段统计不能当作未参与研究的独立留出证据；当前材料不足以支持文档对过拟合风险较乐观的判断。

建议后续保留两个明确实验：各分支原生实现的复现表，以及原生信号在固定共同风险预算下的比较表。把参考组命名为 `wzy_v71_reference` 或直接使用 X 的冻结原版信号，并冻结数据哈希、源码提交、实际生效参数和执行配置，再进行未参与选择的新窗口验证。
